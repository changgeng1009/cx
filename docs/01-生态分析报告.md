## 二、生态分层（决定 Adapter 怎么接）

所有项目按**接入方式**而非按功能分类，因为接入方式决定了 Adapter 的形态：

```
┌─ Layer A · 进程级自动化（能跑在本机，可控性最高）
│   Samueli924/chaoxing、Advanced-ChaoXingBot、Mortal004/Xuexitong_shuake、
│   yatori-go-core、liuyunfz/chaoxing_tool、FxxkStar、PyJun/Mooc_Downloader
│   → Adapter 形态：subprocess + 配置文件 + 日志解析
│
├─ Layer B · 浏览器脚本（能力最全但不可编排）
│   uxuescript、chaolucky18/xuexitongScript、chaoxing-toolkit、XuexitongJSFork、
│   ColdThunder11/ChaoXingDownload、chaoxing-work-export、xuexitong-ppt-downloader
│   → Adapter 形态：Playwright/ScriptCat 注入 + postMessage 桥接
│
├─ Layer C · MCP 服务（可直接被 Agent 调用）
│   DanMo661/Xuexitong-mcp、K4F7/chaoxing-mcp、OSSKn4w7/chaoxing-mcp、
│   Aemiser/chaoxing_mcp、Cr-GH0/chaoxing-agent
│   → Adapter 形态：MCP stdio 客户端 或 直接复用其 HTTP 层
│
├─ Layer D · 题库/解题服务（纯数据，最容易接）
│   destoryD/chaoxing-api、notnotype/xxt、chaoxing-toolkit 的 /api/search、
│   上游内置的 TikuYanxi / TikuLike / TikuAdapter / AI
│   → Adapter 形态：HTTP API
│
└─ Layer E · 扩展能力（本平台非核心，独立评估）
    签到：ChaoxingSignFaker、chaoxing-sign-app、XBT
    下载：Mooc_Downloader、ChaoXingDownload
```

## 四、五个决定架构走向的发现

### 1. 没有任何单项目能覆盖你的全部需求
实测下来，能力天然分裂成两半：

- **"读"侧**（课程/章节/进度/作业/通知/考试）→ 只有 Layer C 覆盖好，且**唯一成熟的是 MIT 的 Xuexitong-mcp**（但很新）
- **"写"侧**（视频/音频/文档/PPT/切章/答题）→ 只有 Layer A 覆盖好，且**全是 GPL-3.0**

**这不构成障碍，反而是选择 Adapter 架构的最强理由**——单点接入任何项目都会缺一半。

### 2. 多账号是编排层职责，不是 Adapter 能力
扫描了全部候选，**没有任何一个 CLI/库项目原生支持多账号**。Layer B 里 `chaoxing-sign-app` 提到"多账号批量签到"，但那是 App 内部状态，不对外暴露接口。

→ **多账号必须由 Orchestrator 实现**：每个账号一份独立凭据 + 独立工作目录 + 独立子进程。这反而更干净（进程级隔离，一个账号的风控不会污染另一个）。这直接决定了 Adapter 契约里必须有 `account_id` 和 `workdir` 概念。

### 3. GPL 传染性必须靠"进程边界"解决，不能靠"小心一点"
你的原则 3 说"不把第三方逻辑复制进统一层"——这条恰好也是**唯一正确的法律解法**：

- ❌ 不能做：`import chaoxing.api.base`（import 即构成衍生作品，统一层被迫 GPL-3.0）
- ✅ 要做的：`subprocess` 调 `python main.py -c config.ini`，通过**文件 + stdout** 交换数据（进程边界 = 许可证边界）
- ⚠️ 特别注意：`Mortal004/Xuexitong_shuake` 是 `NOASSERTION`、`chaolucky18/xuexitongScript` 和 `chaoxing-toolkit` **无许可证**——无许可证 ≠ 可以随便用，默认是"保留所有权利"。这三个在纳入前必须先读 LICENSE 原文

**唯一可安全 import 的是 MIT 项目**：`yatori-go-core`、`DanMo661/Xuexitong-mcp`、`destoryD/chaoxing-api`、`hazuki-keatsu/xuexitong-ppt-downloader`。

### 4. 你的 14 条对外命令里，有 3 条的语义需要先澄清
- `run_video_tasks` / `run_reading_tasks` —— A1 只暴露"整门课跑一遍"，**没有单任务类型的入口**。要实现这两条，要么把任务类型过滤下沉到 Orchestrator（扫出任务清单后只把目标类型交给 Adapter），要么等 Adapter 支持。这决定了 `scan_tasks` 必须是**一等公民**而不是附属功能。
- `pause` / `resume` —— 第三方项目**全部不支持**进程内暂停。可行实现只有两种：① 进程级 SIGSTOP/SIGCONT（Windows 上是挂起线程，不可靠）；② **协作式**：Orchestrator 在任务点边界检查暂停标志，然后把子进程优雅停掉、记录断点、`resume` 时用 `-l 课程ID` 重新进入并跳过已完成任务点。**②才是正解**，因为学习通本身支持"已完成的任务点跳过"。
- `retry` —— 第三方项目内部的重试策略是黑盒（A1 的 `notopen_action=retry` 是"重试上一个任务点"，语义和我们要的"重试失败任务"不同）。所以 **retry 必须由 Orchestrator 定义语义**：针对 `failed` 的任务记录重放，而不是重启整个课程。

### 5. 风控是最大的单点风险，必须在契约层面体现
`DanMo661/Xuexitong-mcp` README 里作者原话："学习通对高频请求有风控，请不要用它做批量爬取、定时轮询间隔过短……账号是自己的，封了别哭。"

→ 统一层必须有**全局限流器**（这个能力和具体的 Adapter 无关，是横切关注点），并且要把"检测到风控"识别为 `blocked` 状态而不是 `failed`。

## 五、能力缺口（没有任何现成项目提供）

| 缺口 | 说明 | 缓解方案 |
|---|---|---|
| 统一进程内暂停/恢复 | 全部项目不支持 | Orchestrator 协作式暂停（见 §4.4） |
| 统一任务状态机 | 全部项目日志格式各异 | Orchestrator 侧状态机 + 日志适配器 |
| Adapter 失效探活 | 无 | 主动 capability probe（轻量调用 + 结果断言） |
| 跨项目 fallback | 无 | Task Router 实现 |
| 多账号编排 | 无 | 独立 workdir + 独立凭据 |
| 统一日志 | 无 | 结构化 JSON 日志，见规范 §6 |
| 浏览器脚本编排 | 无 | MVP 排除，后续用 Playwright 桥接 |

3. **部分项目无法确认默认分支**（`Mortal004/Xuexitong_shuake`、`unraous/uxuescript` 的 README 抓取 404），其能力描述仅来自仓库搜索结果的官方 description 字段。
