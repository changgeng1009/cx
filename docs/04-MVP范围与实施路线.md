# 04 · MVP 范围与实施路线

> 阶段：第四步（确定最小可运行 MVP）
> 原则：**先让骨架跑通，再接真实项目**。理由见 §6。

---

## 1. MVP 目标

### 1.1 目标（一条闭环）

```
list_courses → scan_tasks → run_chapter → status → pause → resume → stop
```

这条链路一旦跑通，架构的**全部关键机制都被验证过**：注册表、路由、进程隔离、进度解析、状态机、断点、日志、fallback。

### 1.2 MVP 明确不做

| 不做 | 原因 |
|---|---|
| 浏览器自动化（`C38`） | 不可编排，需要 Playwright 桥接，成本远高于收益 |
| 签到能力 | 与"刷课"是独立问题域，应做独立插件 |
| 多账号 UI / 账号管理界面 | 数据层支持即可（`accounts/` + `account_id` 参数），M3 前不做交互 |
| 题库自建 | A1 内置 4 种 provider + AI，直接用，不自建 |
| 全 42 项能力 | 只做 §2 列出的 18 项 |
| 上游项目升级自动化 | MVP 用手工 `git checkout <sha>`，不做自动升级 |

### 1.3 MVP 覆盖的能力（18 项）

| 组 | 能力 | 由谁提供 |
|---|---|---|
| 认证 | `C01` `C02` `C03` | A1 / C1 + Orchestrator 兜底 |
| 结构 | `C06` `C07` `C08` `C10` `C11` | C1 为主，A1 兜底 |
| 扫描 | `C09` | C1（章节级）+ Orchestrator 细化（**MVP 内最不确定的一项**） |
| 执行 | `C12` `C13` `C14` `C18` `C19` `C20` | A1 |
| 读取 | `C29` `C31` | C1 |
| 系统 | `C04` `C37` `C40` `C41` `C42` | Orchestrator 自建 |

`C22`/`C23`（题库/AI）不进 MVP 代码，但**必须在配置层打通**——否则 `C26` 章节测验会被上游自动跳过，导致"课程跑不完"的假象。

## 2. 验收标准

MVP 完成的判定不是"代码写完了"，而是下列每一条都能**实际跑出预期结果**：

### 2.1 离线可验收（无需真实账号）★ 优先

| # | 验收项 | 判定方式 |
|---|---|---|
| V1 | 契约完整性 | 14 条命令全部有 Envelope 返回，字段齐全（含 `fallback_trace`） |
| V2 | Adapter 契约测试 | Mock Adapter 通过全部 18 项能力的 `invoke` 契约测试 |
| V3 | 状态机全覆盖 | 8 状态 × 合法/非法转移全部有测试，非法转移被拒绝 |
| V4 | **Fallback 可验证** | Mock 主 Adapter 注入 `not_supported` / `transient`，Router 正确 fallback 且 `fallback_trace` 完整 |
| V5 | **不隐藏失败** | 全部 Adapter 失败时，返回 `ok=false` + 每层失败原因，**不得**返回空数据伪装成功 |
| V6 | 风控熔断 | 注入风控特征响应 → 状态 `blocked` + 账号冷却，且**未**触发 fallback |
| V7 | 断点正确性 | `pause` 后 `state.json` 的 `completed_task_points` 准确；`resume` 只跑剩余 |
| V8 | 日志完整性 | 每条日志含 Adapter/课程/章节/任务类型/起止时间/成败/错误 |
| V9 | 凭据不外泄 | grep 全部日志与返回体，无明文密码/完整手机号 |
| V10 | GPL 隔离 | 静态检查：统一层无 `import` 任何 `upstreams/*`，`upstreams/` 内无本层写入 |

## 6. 为什么 M0 先做 Mock，而不是"直接接 A1 跑起来"

直觉上最快的路径是"clone A1，包一层 subprocess，跑一遍"。**这条路会把所有风险堆到最晚才暴露**：

| 如果先接真实项目 | 如果先做 M0 |
|---|---|
| fallback 逻辑只有 1 个 Adapter，**无法验证** | 用 Mock 注入故障，fallback 全覆盖 |
| 状态机靠"跑一次看看"，边界情况（暂停/风控/超时）几乎不可能自然触发 | 故障注入，边界全覆盖 |
| 账号存在被风控的真实风险 | 零风险 |
| 上游改版 → 分不清是统一层 bug 还是上游 bug | Mock 通过后再接，归因清晰 |
| 无法离线回归 | `pytest` 随时跑 |

M0 的 Mock Adapter 不是什么"测试脚手架"，它是 **Router 和状态机的可验证性基础**。你的原则 6（自动选择 + fallback + 明确错误 + 不隐藏失败）如果没有 M0，就只能靠"读代码觉得对"。

## 7. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **账号被风控/封禁** | 中 | 🔴 高 | 全局限流 + 风控检测熔断 + `--dry-run` 优先 + 首次实测用手动控制的短任务 |

| **C1 项目过新（0★/6天）** | 中 | 🟡 中 | 只当读侧优选，A1 作为读侧兜底；必要时按其 README 的协议备忘自建最小读侧 Adapter |
| **`C09` 任务点类型拿不到** | 中 | 🟡 中 | 三级方案见 `02` §4；最坏降级为"整章执行 + 明确告知" |
| **Python 3.13 环境依赖** | 低 | 🟢 低 | 托管 venv 已就绪；A1 要求 3.13+，与本层一致 |
| **上游许可证变更** | 低 | 🟡 中 | `upstreams/LOCK.json` 记录许可证快照，升级时重新核对 |
| **使用本工具的合规性** | — | 🟡 中 | 上游 GPL 项目均声明"仅用于学习交流，禁止盈利"；使用可能违反学习通用户协议。**建议在个人账号上、以最小必要频率使用**，并理解风险由使用者承担 |
