# 06 · 浏览器隔离约定

> 建立时间：2026-09-17
> 触发原因：使用者提出两条硬约束——**不许动日常 Chrome**，**不许动其他 Agent 正在占用的 Edge 窗口**（Claude 当时正用它做 BOSS 直聘自动化调试）。

---

## 一、为什么这件事必须写成代码

"别用日常浏览器跑自动化"这句话，写在文档里迟早会被破坏。破坏方式非常自然：某个 Adapter 作者（包括未来的我）想快速验证一下，顺手写一句

```python
subprocess.Popen(["msedge.exe", url])          # ❌ 灾难
```

后果是：**这次启动会附着到你已有的默认 profile 实例上**——也就是 Claude 正在调试的那个窗口。轻则多开一个标签页打断对方的自动化，重则两套自动化脚本争抢同一个会话。

所以本约定不是"注意事项"，而是 `orchestrator/browser.py` 里的**强制入口**：启动浏览器必须走这个模块，而它在结构上**拒绝系统默认 profile**。

---

## 二、三个必须知道的技术事实

### 1. Chromium 的 profile 单例锁是按 `user-data-dir` 分的

不同的 `user-data-dir` → 完全独立的浏览器进程、独立的窗口、独立的 cookie 与扩展，**互不影响**。这不是"技巧"，是 Chromium 的既定行为。

所以 `--user-data-dir` 不是可选优化，而是**隔离的唯一手段**。

### 2. 不带 `--user-data-dir` 启动，一定会附着到已有实例

`msedge.exe https://xxx` 这种写法会复用当前运行的默认 profile 实例，表现就是"多开了一个标签页"。这正是我们要避免的情形。

### 3. Edge / Chrome 136 起，对**默认 profile** 禁用 `--remote-debugging-port`

这条很容易踩：在 136+ 上用默认 profile 启动并想开 CDP，端口**不会被监听**，或者调试连接被拒。

也就是说，**想让自动化拿得到 CDP，反而必须用独立 profile**。使用者的隔离要求与自动化的技术需求在这里刚好一致——这是个很舒服的巧合。

---

## 三、我们的方案

| 项 | 值 | 说明 |
|---|---|---|
| profile 目录 | `<项目根>\.browser\edge-profile` | 放在项目内，让"用的是哪个 profile"**一眼可见**。隔离性如果不可见，就等于不存在 |
| CDP 端口 | **9333** | 刻意避开 9222（业界最常见默认值，极易与其他工具撞端口） |
| 绑定地址 | `127.0.0.1` | CDP 只监听本机，不暴露到局域网 |
| 浏览器 | 系统 Edge | 找不到时可用 `ORCH_EDGE_BINARY` 指定 |
| 进程记录 | `<项目根>\.browser\browser.pid` | 只记录我们自己的 PID，用于告诉你"哪个进程是我的" |
| 版本控制 | `.browser/` 已 gitignore | profile 体积大且含登录态，绝不入库 |

### 环境变量

| 变量 | 作用 |
|---|---|
| `ORCH_EDGE_PROFILE` | 覆盖 profile 目录 |
| `ORCH_EDGE_DEBUG_PORT` | 覆盖 CDP 端口 |
| `ORCH_EDGE_BINARY` | 指定浏览器可执行文件 |

## 四、代码层面的守卫

`browser.assert_isolated(path)` 会**在启动前**拒绝以下路径：

- 本机实测存在的 Edge / Chrome 默认 profile 目录（`system_profile_dirs()` 返回）
- 位于上述目录**之内**的任何子路径（例如 `User Data\Profile 3`）
- 文件系统根目录
- 用户主目录

被拒绝时的报错是明确的，而不是静默降级：

```
IsolationError: 拒绝启动：C:\Users\...\Microsoft\Edge\User Data 是本机浏览器的默认 profile。
用它启动会把你日常浏览器的会话暴露给自动化，并可能干扰正在使用该 profile 的其他程序。
```

这层守卫由 `tests/test_browser.py`（22 项）覆盖，其中包括"**遍历本机真实存在的默认 profile，逐个断言必须被拒**"——所以这台机器上只要装了 Chrome/Edge，误用就一定会被测试拦住。

同时测试还锁定了几个容易回退的细节：

- `--user-data-dir` 与 `--remote-debugging-address=127.0.0.1` 必须始终存在
- 默认端口不能等于 9222
- `plan()` 必须**只读**（不创建目录、不启动进程）

## 五、怎么用

```bash
# 查看决议：profile 路径、端口、浏览器、本机禁区清单、CDP 是否在线
python -m orchestrator.browser --show

# 启动独立实例（窗口会弹出来，与日常浏览器、其他 Agent 的窗口互不影响）
python -m orchestrator.browser --launch

# 启动并直接打开学习通登录页
python -m orchestrator.browser --launch --url https://i.chaoxing.com

# 只探测 CDP 是否在线（不启动任何东西）
python -m orchestrator.browser --status

# 查看怎么停止
python -m orchestrator.browser --stop
```

Windows 上也可以直接双击项目根目录的 **`启动独立浏览器.cmd`**（会自己找 Python，透传 `--url` / `--port`）。

### 停止方式

**推荐直接关掉那个 Edge 窗口。** 这是最简单也最安全的做法，因为独立 profile 的窗口关掉后不会影响任何其他实例。

`--stop` 只打印说明，**不执行**：

```
⚠️ 不要用「结束所有 msedge.exe」这类命令 —— 会杀掉其他 Agent 正在使用的 Edge 窗口。
```

这条警告是有意的。我不提供"批量杀 Edge"的功能，因为那正是使用者明确要求避免的破坏方式。要做精确清理，只需带上 PID（记录在 `.browser/browser.pid`）并确认该进程命令行里含本项目的 profile 路径。

## 六、后续 Adapter 必须遵守的约定

任何需要浏览器自动化的 Adapter（当前只有 `C38` 浏览器自动化、以及签到里的位置/二维码/拍照签到），必须：

| # | 约定 | 原因 |
|---|---|---|
| B1 | **不得自行 `Popen` 浏览器**，一律走 `orchestrator.browser` | 隔离守卫生效的前提 |
| B2 | 一律使用项目内的独立 profile | 与 B1 配套 |
| B3 | 需要扩展（Tampermonkey / ScriptCat）时，**装进这个独立 profile**，不要装进日常浏览器 | 油猴类脚本权限很大，且 MV3 下行为有变，隔离起来更安全 |
| B4 | 不得使用 `--user-data-dir` 缺省的启动方式 | 见技术事实 2 |
| B5 | 不得对 `msedge.exe` / `chrome.exe` 做进程级批量清理 | 见停止方式 |

### 关于油猴类脚本

如果将来要走脚本路线（`unraous/uxuescript`、`chaoxing-toolkit`、`chaoxing-work-export`），扩展就装在**这个独立 profile** 里。这带来两个好处：

1. 你的日常 Chrome 依然干净；
2. 脚本失效时，直接删掉 `.browser/` 目录重来，不会留下任何残留。

需要注意 `chenhuilin2/chaoxing-work-export` 要求的是**脚本猫（ScriptCat）**而非 Tampermonkey，两者可共存于同一 profile。

### 启动失败的诊断顺序

使用者报告"没拉起来"时，按这个顺序查（`--diagnose` 会一次全查完）：

1. **浏览器可执行文件是否存在** —— 找不到时用 `ORCH_EDGE_BINARY` 指定
2. **端口是否被占** —— `9333`；占用则换 `--port 9334`
3. **CDP 是否在线** —— 这是唯一有意义的存活判据
4. **PID 记录里的进程是否还活着** —— 记录在而进程死 = "启动后立刻死了"
5. **浏览器日志** —— `.browser/browser.log`，**浏览器自己打印的原因**

日志这一环是补上去的：最初启动时把 stdout/stderr 丢进了 `DEVNULL`，
浏览器报的错全被吞掉，使用者只看到"没反应"。现在改为落盘，
并且 `--launch` 在 CDP 始终未就绪时会**明确报失败**，而不是含糊地说
"可能仍在初始化"。

> 同理，`cookies_login` 在 CDP 不可达时会**立即**返回 `CDP_UNAVAILABLE`，
> 不再傻等满 `--timeout`（默认 300 秒）才报一个误导性的"登录超时"。

### ⚠️ 限制：浏览器必须由使用者自己的终端启动

Agent 的工具运行在**沙箱**里，命令结束后沙箱会回收该次调用派生的子进程。因此：

- 我**可以**验证启动参数正确、CDP 能起来（已实测）；
- 我**无法**让浏览器窗口常驻——沙箱一收，窗口就跟着没了。

所以常驻实例应当这样启动（在你的终端里，不是通过我）：

```bash
cd /d D:\CodexWork\学习通刷课脚本
python -m orchestrator.browser --launch --url https://i.chaoxing.com
```

或者直接双击 `启动独立浏览器.cmd`。启动后窗口会一直留着，CDP 也持续可用。

> 这个限制只影响"谁来按下启动键"，不影响隔离性：无论谁启动，走的都是同一套 `--user-data-dir` 独立 profile，都不会碰到你的 Chrome，也不会碰到其他 Agent 的 Edge 窗口。

### 关于"我无法从沙箱里枚举进程"

同一原因也导致我在沙箱里拿不到 `tasklist` / `netstat` 的输出。所以本方案**没有**采用"先检测端口占用再决定"的策略，而是改用**结构上不可能冲突**的设计：

- profile 放在项目内的唯一路径 → 其他 Agent 不可能用同一目录；
- 端口选 9333 而非 9222 → 避开最常见默认值。

验证不了环境时，就用"让冲突不可能发生"的设计来替代"检测冲突"。这比依赖检测更可靠。
